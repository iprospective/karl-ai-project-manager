# NORMS·runtime KERNEL — seul fichier NORMS préchargé ; lire EN ENTIER chaque session
Réécriture dense pour LLM (RM3037, essai) de `norms/src/` ; source humaine `norms/src/NORMS-KERNEL.md`. Généré ⇒ ne pas éditer.
Contenu : (A) garde-fous permanents, (B) index mots-clés → module à ouvrir quand le cas se présente. Module = détail, fait foi ; KERNEL = obligation d'y aller. Modules runtime : `norms/runtime/<nom>.md`.

## A. Garde-fous permanents
1. **Outillage.** Tout changement d'état de tâche, branche, repo/submodule, ticket Redmine passe par le script/skill PM dédié. Pas d'outil = trou à combler (créer le script), jamais une exception manuelle.
2. **Commit+push.** Toute modif d'un fichier PM ou du workspace de code : `git add <chemins explicites>` + commit + push immédiat. Jamais `git add .`/`-A` ; ne stager/committer que SES modifs (repos partagés dirty en concurrence).
3. **Branche par ticket + MR (dépôts de CODE).** Branche `<RMid>-<slug>` tirée de la branche d'intégration, jamais dessus ; CF Redmine « GIT Branche ». Livraison = MR sur le remote, jamais un merge poussé direct. Branche distante CONSERVÉE après merge (supprimer = accord explicite ; autoriser un merge ≠ autoriser une suppression) ; ménage des branches mergées en local seulement. Aucun commit/push direct sur une branche protégée : intégration (`dev`) ET prod (`main`/`master`), promotion `dev`→prod incluse ; enforcé côté GitLab (push direct interdit, merge de MR seul).
   Exception dépôts de DONNÉES PM (`*-core`) : `.mmi-pm/` ou `.mmi-pm-client/` RÉEL à la racine (symlink = workspace de code, pas un core) ; ni code ni revue, l'historique git est l'audit ⇒ push direct sur sa branche de prod (`push=Developer`), les scripts pm-* y écrivent sans branche ni MR ; `allow_force_push=false` reste posé. Plomberie muette ⇒ #15.
4. **Sync statut MD↔Redmine.** Tout changement de `status`, dans le même cycle : Redmine (status_id + note) + frontmatter (`status`, `status_history`, `updated`) + `.log.md`. Toujours `pm-task-status-update`, jamais un statut en dur ; cibles valides par `--list-next`. Parent → `ferme` seulement si toutes ses sous-tâches sont fermées, sinon Redmine refuse SILENCIEUSEMENT (PUT 204, statut inchangé, faux air de permission « Edit issues » manquante) : ne pas s'acharner ni conclure « droits », vérifier `GET /issues/<id>.json?include=children` (+ `allowed_statuses`).
5. **Prise ⇒ auto-assignation.** `en_cours` implique s'assigner (`assigned_to`) dans le même mouvement. Pas d'`en_cours` flottant.
6. **redmine_id obligatoire.** Toute tâche/projet MD est reliée à son Redmine ; fichier `RM{id}_…` cohérent avec `redmine_id`.
7. **Filtrage IA.** Tout ticket créé par le PM porte le CF `IA = "IA"` (posé au POST). Pas de MD local sans CF IA.
8. **Estimation.** Tokens + temps à la création ; à la prise si absente.
9. **Description vivante.** Checklist ou état en prose ⇒ tenus à jour DANS la description (pas seulement en note) + `done_ratio` au fil de l'eau.
10. **Sécurité prod.** Rien qui puisse modifier/casser la prod sans consentement humain explicite POUR CETTE ACTION : inspecter en lecture seule, proposer la commande exacte, attendre ; un accord ne vaut pas pour l'étape suivante. Restauration préalable : infra opensvc/LXC/ZFS ⇒ snapshot ZFS du conteneur depuis l'hôte AVANT la MEP (`om <svc> sync update --rid sync#root_hour`), tient lieu de sauvegarde (pas de dump ad hoc en plus) ; son nom se logue avec le rollback.
11. **Secrets.** Jamais commités, loggués, écrits sur disque ni en transcript ; jamais demander le secret de déverrouillage d'un vault (master password, passphrase).
12. **Traçabilité par étape.** Chaque étape significative : commit + note Redmine (détail + réf commit + temps/tokens) + entrée `.log.md`.
13. **Jamais d'identifiant séquentiel prédit** (RM-id, iid de MR…). Redmine ET GitLab séquencent globalement à l'instance, en concurrence : « dernier vu + 1 » INTERDIT. Tout numéro se capture de la sortie d'un script : `ID=$(pm-task-add … --porcelain)` ou `--start-branch` (atomique) ; `IID=$(pm-mr create … --porcelain)` ou `pm-mr create --merge` ; `pm-mr merge --expect-rm <id>` (garde). Gardes auto : refus pm-mr sur branche divergente, hook pre-push.
14. **Projet→Redmine sans ambiguïté, jamais par slug nu.** Cibler par `client/slug` (`matnat/infra`) ou `redmine.project_id` unique (`matnat-infra`) : plusieurs clients partagent un slug (`infra` chez abatik/calicote/calyclay/matnat/pisceen), un match « premier arrivé » écrit dans le mauvais projet. Slug ambigu ou projet sans `redmine.project_id` (`meta.yml`) ⇒ erreur bloquante, jamais de choix silencieux. `PMConfig.resolve_project_ref(ref, require_redmine=True)`.
15. **Plomberie PM muette, jamais le sujet d'une question.** La mécanique git des `*-core` (auto-commits `pm(...)`, push, branche, MR, « ✓ commité », hash) ne figure JAMAIS dans la restitution : restituer le fond du ticket et le code livré (une MR de CODE se raconte). Exception : un auto-push qui échoue se signale en une ligne. Outillage idem : `pm_git` muet sur le nominal (`git.verbose: true` pour déboguer). Vaut en LECTURE : une question non qualifiée (« mergé en main ? », « poussé ? », « où en est la branche ? ») porte sur les dépôts de CODE et le dépôt du projet PM, jamais sur un `*-core` non nommé ; le support (fiche dans `<Projet>-core`) n'est pas le sujet, un ticket porte sur le code de `repos/`. S'applique au moment de rédiger la réponse, sans fichier ouvert ; se re-viole après chaque compactage : le relire.
16. **Métriques avant conclusion (incidents).** Parc supervisé par Zabbix (`https://zabbix.iprospective.fr`, JSON-RPC, `ZABBIX_API_TOKEN` du `.env` PM : CPU/charge/réseau, workers Apache, pools PHP-FPM, MySQL). Jamais conclure sur la cause d'un incident depuis les seuls logs de la machine : ils disent ce qui a été journalisé, pas ce qui n'a pas pu l'être (service engorgé cesse d'écrire ; Apache journalise en FIN de requête ; rsyslog affamé n'écrit plus ⇒ imite une panne réseau). Un agent local qui « mesure » n'est pas fiable tant que Zabbix ne corrobore pas (incident RM2455 : deux diagnostics réfutés, cause réelle pool PHP saturé → workers Apache épuisés → `MaxRequestWorkers`, trouvée en 3 requêtes Zabbix). → `knowledge/zabbix/api.md`
17. **Tests au fil de l'eau.** Coder = livrer les tests avec le code : TDD par défaut sur la logique, unitaires + fonctionnels/workflow dès la conception, tous les cas (tests auto ET protocole de test). `mmi-pm test` vert avant livraison (front/cockpit ⇒ tests node même MR). Non automatisable (rendu navigateur, intégration tierce) ⇒ recette humaine + justification tracée ; jamais « pas de test ».
18. **Propriété, verrou, journal.** Redmine = mutex, fichiers MD = contexte : l'assignation Redmine donne la propriété du `RM{id}.md` (worker assigné seul R+W ; parent : orchestrateur ; `project.md` : orchestrateur ; autres en lecture) ; accès concurrent réel sérialisé par ressource (`flock`) ; données communes partagées (groupe `pm`), karl = admin via `sudo` humain. Optimistic locking sur tout `.md` : lire `updated`=T1 → préparer → relire ; ≠T1 ⇒ relire et recommencer ; =T1 ⇒ écrire, `updated`=T2. `.log.md` : append-only (jamais effacer/éditer), tout agent peut appender, ordre non garanti acceptable, pas de locking. Entrée : `## <ISO minute> — <agent> (<modèle>)` / `Tokens : N | Durée : N min` / ligne vide / résumé (fait, décisions, problèmes).

## B. Index mots-clés → module [outils]
- **schema** : cascade client→projet→tâche, nommage `RM{id}_…`, frontmatter tâche, énumérations (type/status/priority/close_reason/target_env…), lecture du contexte par niveau
- **structure-reference** : résoudre un chemin PM (jamais en dur), lien workspace↔PM [`pm_paths.PMConfig`, `pm-sync-links`⚠]
- **git-mep** : branche de ticket, commit/push, MR, worktree multi-tickets, cycle dev→test→MEP, `deploy_actions` (procédure de MEP), branches de référence, identités/transport forge, PAT J-7 [`pm-branch-start`, `glab`, `pm-task-deploy`, `pm-token-check`]
- **git-mep-pratique** (hors précharge) : transport git qui résiste (SSH/token, submodules), API GitLab de travers, préparer une MEP, ticket d'interface [`pm-mr`, `pm-promote`]
- **status-workflow** : changer un statut, prendre une tâche, fin de dev / routage test (`requires_agent_test`), ticket qui revient (a_corriger), machine d'états, mapping Redmine, attribution, flux court micro-tâche (≤ 30 min sans code) [`pm-task-status-update --list-next`, `pm-task-take --no-branch`, `pm-task-add --retro`, `redmine-fetch-updates`]
- **status-workflow-pratique** : transition exacte, qualifier en étude, rédiger un CDC (proposition d'implémentation obligatoire dès que l'étude débouche sur du code : `pm-task-implementation`), transition refusée (assignee-only), ticket revenu avec notes
- **testing** : garde-fou 17, écrire les tests avec le code, protocole de test [`mmi-pm test`, `pm-task-protocol`, `pm-task-deliver`]
- **session-tooling** : quel outil pm-* pour quelle opération, cheatsheet, garde de périmètre, registre des DEMANDES (chaque demande du demandeur, même ticketée dans la minute : `pm-session-status.py request`), NOTIFICATIONS d'événement notable (secret affiché, refus, garde-fou, outil en défaut, décision bloquante : `pm-session-status.py notify`), capture d'un RM-id, tâche dans le mauvais projet [`pm-task-move`]
- **redmine-hygiene** : checklist, description périmée, done_ratio [`pm-task-description-update`]
- **redmine-sync** : donnée/artefact partagé Redmine↔PM (champ, vue, template, doc, métrique : parité) ; livrable documentaire (audit, CDC, spec, roadmap, rapport) = markdown en repo, jamais un artefact LLM-spécifique [`pm-wiki-sync`]
- **redmine-reference** : CF IA, ids Redmine, résolution projet (#14), contrôle avant session Redmine [`redmine-config-check`]
- **traceability** : commit / étape significative (note + log + métriques), décision ou arbitrage à journaliser au fil de l'eau [`pm-task-report`]
- **roi-pricing** : estimer, ROI, prioriser [`pm-task-add`, `pm-task-tick`, `priority.py`]
- **task-links** : lier / dépendre / parenter des tickets [`pm-task-link`]
- **environments** : me connecter à / référencer un env (`ssh_alias`), secrets et vaults (#11) [`resolve-secret.sh`]
- **environments-reference** (hors précharge) : écrire/éditer un aspect `environments.md` (noms d'env, champs, `post_deploy`, logs) [`templates/aspects/common/environments.md`]
- **project-creation** : créer projet / entité, bootstrap, memberships [`pm-project-new`, `pm-project-bootstrap`, `pm-client-new`]
- **project-modeling** : projet multi-clients / implémente un général, aspects, CDC, contacts [`pm-doctor`, `pm-sync-views`⚠, `pm-client-contact`]
- **audits** : audit demandé (site, sécurité, infra, DNS, mail, conformité) : lire l'existant AVANT de mesurer ; findings dans `iprospective/audits`, remédiation dans le projet propriétaire [skill `mmi-audit`, `new-audit-session.sh`]
- **collaboration** : je suis l'orchestrateur (assignation, sous-tâches, propagation), multi-utilisateur
- **summarizer** : fichiers auto (Changelog/Pistes/Remarques)
- **governance** + `norms/MAINTAINING.md` : changement de SURFACE (outil, flux, cockpit UI, archi/dev) ⇒ doc vivante dans la MÊME MR (Changelog · README · aide cockpit · DEVELOPMENT) ; changement TRIVIAL du repo PM (glossaire, coquille) : MR due, ticket non (`pm-mr create --no-ticket`) ; déploiement, versionning NORMS, skills, coût de contexte d'un module/rôle [`pm-norms-assemble`, `pm-norms-doctor`, `pm-context-budget`]
- `knowledge/zabbix/api.md` : incident, historique de charge d'une machine (#16) [JSON-RPC, `ZABBIX_API_TOKEN`]
