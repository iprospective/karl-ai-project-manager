# runtime·environments — envs d'exécution, connexion, secrets/vaults
Ouvrir quand : je me connecte à / référence un environnement · je manipule un secret (vault, quel qu'il soit). Outils `ssh_alias`, `resolve-secret.sh`. Source : `norms/src/modules/environments.md`. Format de l'aspect (noms d'env admis, champs `ssh_alias`, `post_deploy`, `logs.*`, `env_vars[]`…, conventions de chemins) : `environments-reference`.

## Aspect `environments.md`
Déclare les envs d'exécution d'un projet (dev, test, staging, prod…), distinct de `hosting.md` (provider/coûts/DNS). Frontmatter liste `environments[]` (template `templates/aspects/common/environments.md`). Cascade : niveau client (défauts host, user, secrets_source) et projet (surcharge/complète).
Connexion SSH : `ssh_alias` s'il est renseigné (porte `ProxyJump`/clés de `~/.ssh/config` ; convention OVH alias = nom du conteneur), sinon `ssh_target` (`user@hostname`). `host`/`user` indicatifs (préfixe des logs, contexte), pas la commande.
Tâche : `target_env: <name>` ⇒ `test_url` déduit de `environments.<target_env>.url` sauf surcharge explicite. Envs de session par ticket : `pm-env-session create` écrit `http://<repo>-rm<id>.lxc/` (frontmatter + CF « Environnement de test »), `teardown` les VIDE (jamais d'URL morte affichée).
Worktree résolu PAR BRANCHE, jamais par chemin deviné : vhost/`env_name` = identité stable `<repo>-rm<id>.lxc`, mais le worktree se trouve via sa branche `<id>-*` (`git worktree list`), quel que soit le dossier (`envs/<repo>-rm<id>`, `envs/<repo>-dev-<id>-s<seq>`, renommé). `pm-env-session create` et `pm-cockpit-test-env create` RÉUTILISENT un worktree déjà monté (`pm-branch-start --worktree`) et posent vhost/runtime par-dessus (idempotent, `DocumentRoot` réécrit). Résolveur `pm-env-session.worktree_for_branch()`.

## Secrets — vaults déclarés
Jamais commités (ni repo PM public, ni repo projets privé) : vivent dans un gestionnaire de secrets, référencés par URI. Plusieurs vaults coexistent : instances du registre providers `pm.config.yml :: providers.servers` (axe `secret`), slug + défaut `providers.defaults.secret`, surcharge par client ou projet. Ex. `vw-ipro {type: vaultwarden, url}`, `kdbx-perso {type: keepass, file}`, `age-acme {type: age, file}`, `op-ipro {type: onepassword, vault}`. AUCUN secret dans cette déclaration (urls, types, chemins seulement).
Identifiants par dev : `~/.config/mmi-pm/.env`, slug normalisé (majuscules, non-alphanum → `_`) : `SECRET__VW_IPRO__CLIENTID`, `SECRET__KDBX_PERSO__FILE`, `…__TOKEN` ; historiques `VAULT_URL`/`BW_CLIENTID`/`BW_CLIENTSECRET` lus en repli.
URI (3 formes valides) : `secret://<instance>/<chemin…>[#champ]` · `secret:<chemin…>[#champ]` (instance par défaut, cascade projet/client) · `vaultwarden://<org>/<collection>/<item>` (historique, supportée définitivement, jamais à réécrire). Ex. `secret://vw-ipro/clienta-agents/prod-db` ≡ `vaultwarden://iprospective/clienta-agents/prod-db`.
Backends : `vaultwarden` (défaut), `keepass` (`.kdbx`, `python3-pykeepass`), `age` (YAML/JSON chiffré, dép. `age`, sans serveur ni compte), `nextcloud_passwords` (app Passwords, mot de passe d'application), `onepassword` (CLI `op` + service account ; CLI hors Debian, jeton payant). Extension : `pm_secrets.register_backend()`.
Chiffré côté client (Passwords avec clé navigateur) ⇒ le backend REFUSE (`unsupported`, nomme le chiffrement) plutôt que livrer un cryptogramme pris pour un mot de passe : un secret pour agents ne va pas dans ce périmètre.
Vaults sans session (`age` par clé locale ; jeton : 1Password service account, mdp d'application Nextcloud) : rien à déverrouiller, ne se verrouillent pas (`lock-vault.sh` n'agit que sur les sessions en mémoire) ; refus rapporté `locked` mais le remède est un NOUVEAU jeton, pas un mot de passe maître. `age` : seuls les droits du fichier protègent, clé `0600` (`SECRET__<SLUG>__AGE_KEY_FILE`), jamais commitée ni dans la déclaration ; la page de santé signale une clé trop ouverte.
Un secret ne passe jamais en argument de commande (`ps`, historique shell) : variable d'env ou stdin (`unlock-vault.sh --stdin`).
Secrets d'un client hébergés chez nous : collection `<client>-agents` du vault iProspective ; instance dédiée seulement pour un intervenant avec son propre outil ou un client qui impose le sien.
Vault par défaut (Organization iProspective) : `<client>` (accès Mathieu seul) · `<client>-agents` (items lisibles par les agents ; membre `karl@iprospective.fr` User read-only) · `iprospective-agents` (secrets internes : Redmine bot, n8n… ; idem). Un seul user d'agents `karl@iprospective.fr`, read-only sur `*-agents` ; les credentials critiques (root SSH, BDD admin, master gitlab) hors scope agents.

## Sessions de vault
Déverrouillage (humain) : `scripts/unlock-vault.sh [-i <instance>]` (demande le secret humain, jamais stocké) ou bouton 🔓 du cockpit (affiché seulement si un coffre est fermé) ; vault sans session ⇒ diagnostic seulement · résolution (agent/script) : `scripts/resolve-secret.sh "<uri>" [champ]` · verrouillage : `scripts/lock-vault.sh [<instance>]` · inventaire : `scripts/vault-list.sh [-i <instance>] [filtre]` · quel vault pour ce projet : `scripts/pm-providers.py resolve secret`.
Daemon `vault-agentd.py` : une session par instance, en mémoire seulement (pas de fichier, pas même tmpfs) ; socket `/run/user/$UID/vault-agentd.sock` (600) ; verrouille chaque instance après inactivité (`VAULT_IDLE_TIMEOUT`, 8 h) et/ou à heure fixe (`VAULT_LOCK_AT_HOUR`, 23 h) ; s'arrête quand plus aucune instance ouverte.

## Règles strictes
1. Jamais demander le secret de déverrouillage ; `resolve-secret.sh` code 2 ⇒ dire « lance `unlock-vault.sh`, ou déverrouille depuis le cockpit » et attendre ; `--stdin` sert à un appelant qui transmet un secret saisi par l'humain (cockpit), jamais à un agent. Code 4 `unreachable` ≠ verrou : config/dépendance manquante (le message dit laquelle).
2. Secrets résolus jamais loggués, écrits sur disque, commités ni en transcript ; un diagnostic nomme les CLÉS trouvées, jamais les valeurs.
3. Rotation des identifiants d'agent trimestrielle (immédiate au moindre doute).
4. Agents 24/7 (cron, n8n) : seulement dans la fenêtre d'unlock manuel ou via un sous-scope dédié explicitement autorisé.
5. URI vers une instance inconnue ⇒ refus, jamais rabattu sur le vault par défaut.
Dans les aspects : `secrets_source: secret://<instance>/<chemin>` (ou `vaultwarden://…`) comme pointeur, jamais la valeur ; lister les items référencés et leur rôle dans `client/security.md` (audit humain).
