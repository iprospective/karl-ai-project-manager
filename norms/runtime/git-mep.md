Outils `pm-branch-start`, `glab`, `pm-task-deploy`, `pm-mr`, `pm-worktree`. Source : `norms/src/modules/git-mep.md`. ## Branches de référence (par projet, `project/overview.md` bloc `git:`)
`repo` (url/alias, ex. `git:sfy/pisceen-dercya/pisceen-prestashop.git`) · `remote: origin` · `prod_branch: main` (défaut ; `master` legacy, migration au fil de l'eau) · `integration_branch: dev` (agrège les devs testés avant MEP) · `preprod_branch: preprod` OPTIONNEL : sa PRÉSENCE active le flux 3 branches longues protégées `dev → preprod → prod_branch` ; absent ⇒ modèle 2 branches `dev → prod_branch`. Seul levier (pas de flag, pas de bypass).
Cohérence : `environments[].branch` — `prod.branch == prod_branch` ; `staging.branch == preprod_branch` si déclaré, sinon `== integration_branch`. Ne pas confondre avec le bloc `git:` de la TÂCHE (`git.branch`, `git.mr_url` = branche de travail du ticket).

## Modèle d'environnements
1 `prod` (depuis `prod_branch`) · 1 `staging` (alias `preprod` ; depuis `preprod_branch` en flux 3 branches, sinon `integration_branch` ; non-régression avant prod) · N `test`/`test-<but>` (tester en parallèle des branches de ticket, par quelqu'un ≠ le dev) · N `dev`/`dev-<dev>`. Noms custom admis par l'enum `target_env` ; chaque env décrit dans `environments.md`.

## Identités & transport forge (multi-utilisateur)
- Jeton forge par dev, karl en repli : cascade des secrets (collaboration § Multi-utilisateur) — token perso `<core>/var/users/<user>/.env` (`<FORGE>_<ROLE>_TOKEN`) d'abord, karl ensuite. L'API forge (MR, protections) utilise ces PAT ; l'auteur d'une MR/branche = le dev.
- Transport SSH-first, token en repli : remotes en alias SSH canonique (`gitlab:…`, `.gitmodules` inclus) ; push/fetch par la clé forge du dev ; repli HTTPS+token (`url.…insteadOf` global + credential helpers) si pas de clé ou submodules sans clé. NE PAS convertir les remotes par dépôt en HTTPS (casse les submodules).
- Abstraction `pm_forge` : GitLab, Gogs (sans API PR → flux lien-compare, push HTTPS+token, SSH port 28022), GitHub ; backend par projet `git config pm.forge`. Voir `pm-mr` / `pm-promote` / `pm-protect`.

## Workflow par ticket
1. Prise : `en_cours` + auto-assignation + branche `<RMid>-<short-desc>` depuis `integration_branch` + CF Redmine `GIT Branche` (id 3). Outil : `pm-branch-start.py <RMid> --from <integration_branch> [--take]` (crée/checkout, pousse le CF, `git.repo`/`git.branch` + log ; `--take` enchaîne `en_cours`).
2. Dev terminé ⇒ `a_tester_dev` : test par agent/personne ≠ dev en env `test`. OK ⇒ `a_tester_demandeur` + réassignation au demandeur ; problèmes ⇒ `a_corriger`.
3. Validation demandeur ⇒ MR de `<RMid>-<desc>` vers `integration_branch` (`dev`), URL dans le CF `GIT PR` (id 4) = trace du merge d'intégration ; merge ⇒ `a_mep` (entre dans le workflow MEP ; le passage AFFICHE la procédure de MEP du ticket, cf. deploy_actions). Rejet ⇒ `a_corriger`.
Exception : ticket sans code à déployer (doc, infra ponctuelle) : `a_tester_demandeur` → `ferme` (`close_reason: resolu`) sans MR ni MEP.

## `deploy_actions` = procédure de MEP du ticket (runbook)
Ce que CE ticket exige en propre, ordonné (migration et ordre, constante à créer, cron, service à recharger, dépôt A avant B, recalcul après coup) ; l'ordre de la liste = ordre d'exécution. Canonique : CF Redmine 8 « Actions au déploiement » ; miroir frontmatter `deploy_actions` (liste, une étape par ligne). Outil `pm-task-deploy` (`--add` / `--set` / `--clear` ; `--pull` si saisi dans l'UI web). Affiché à qui déploie au passage en `a_mep`.
Rédiger au fil de l'eau (quand on écrit la migration), pas à la livraison.
OUI : étapes propres au ticket, cible si non évidente (env, dépôt, machine), point de non-retour, rollback s'il ne se réduit pas à revenir au commit précédent. NON : ce qui est systématique pour l'env (`environments[].post_deploy`, déclaré une fois par env) ; le générique du workflow (MR, merge, `git pull`). Rien de particulier ⇒ liste vide (c'est une réponse) ; pas de remplissage de complaisance (« déployer le code »).
Déclaratif, jamais auto-exécuté ; ne dispense d'aucune garde (consentement par action, snapshot ZFS préalable, garde-fou 10).
Sync : PM → Redmine à chaque écriture ; Redmine → PM à chaque `pm-task-sync`. Un CF vide ne remet JAMAIS le miroir local à zéro (vide = pas d'info) ; vidage volontaire = `pm-task-deploy --clear` (écrit les deux côtés). Reprise de l'existant : `pm-cf-mirror-backfill` (dry-run par défaut, ne remplace jamais du contenu par du vide, signale les désaccords).

## Commit + push systématique
- Auto-commit des scripts pm-* (`pm-task-add/-status-update/-comment/-link/-sync/-report/-metrics-push`) : ils committent et poussent eux-mêmes, atomiquement, les fichiers écrits (`scripts/pm_git.py`, `git commit -- <chemins>` sous verrou local, non-fatal ; `pm.config.yml :: git.autocommit` / `git.autopush`, `--no-commit` par appel) ⇒ RIEN à committer toi-même pour une opération passée par un script PM. La règle manuelle vaut pour les édits libres (aspects, CDC, corps de tâche) et le workspace de code.
- Sur un core : push direct sur la branche de prod (ni repli `dev` ni promotion) ; rejet non-fast-forward rattrapé par `pm_git` (fetch + `rebase --autostash` sous verrou, re-push) ; conflit ⇒ `rebase --abort` + warning. Levée ciblée de « pas de rebase dans l'arbre partagé » : cores seulement, code inchangé. Succès silencieux (`git.verbose: true` pour déboguer).
- Rattrapage : sur un core, chaque auto-commit embarque aussi ce qui est resté non commité depuis > 1 h (dernière modif ; `git.sweep_after_min`, défaut 60 — fiches, `.log.md`, CDC, `reporting.yml`) dans un commit séparé `pm(rattrapage): N fichier(s) laissés non commités > 60 min (déclenché par <outil>)`, poussé avec le nôtre ; < 1 h laissé à la session en cours. Pas de timer ni process dédié. Ne dispense pas du commit immédiat manuel. Débrayage `git.sweep: false` ; journalisé `logs/karl-agent.jsonl` catégorie `pm`.
- Deux périmètres : (1) dossier projet PM côté `{projects_root}` (ai-projects : overview, aspects, `RM*.md`/`.log.md`, `client/`, `memory/`) → repo `gitlab:iprospective/ai-artificial-intelligence/ai-projects.git` ; (2) workspace de code lié (paire de symlinks : `{paths.workspace_link}` côté PM → workspace ; `{paths.reverse_link}` = `.mmi-pm` côté workspace → projet PM) → repo applicatif du workspace (remote canonique `git:`/`gitlab:iprospective/<...>`, PAS ai-projects).
- Règles communes : stager uniquement les fichiers touchés (jamais `git add .`/`-A`) — tous les repos partagés (ai-projects, repo système `project-management` : NORMS, `templates/`, `scripts/`, `pm.*.yml`, et le workspace de code) sont souvent dirty en concurrence ; avant tout commit (1) stager par chemin explicite, (2) relire `git diff --cached --name-only` et confirmer que chaque entrée est de la tâche courante, (3) committer alors ; jamais un fichier qu'on n'a pas modifié soi-même dans la session (ni un non-suivi d'une autre tâche). Message court, langue du repo, entité/projet/tâche. Push systématique (pas « le user pushera » : le repo reflète l'état canonique, sinon vue divergente). Push refusé ⇒ `git pull --rebase` puis re-push ; conflit non trivial ⇒ escalader. Jamais committer un dossier projet PM dans `project-management/` (`projects/` gitignored). Workspace pas encore un repo git ⇒ lacune de bootstrap : (re)lancer la tâche `002-git-repos`, pas « skipper ». Vaut pour tous les agents, interactifs inclus.

## Branche de travail par ticket
`<RM-id>-<slug-court>` (id sans préfixe, 2–4 mots kebab, pas le titre complet ; ex. `1762-etransactions-historique`), créée depuis la branche d'intégration. Frontmatter `git.branch` → la branche, `git.mr_url` → la MR. CF `GIT Branche` (id 3, string) = nom de branche dès la création ; CF `GIT PR` (id 4) = URL de la MR — CF dédiés, pas une note. Livraison par MR, branche distante conservée (jamais supprimée sans accord explicite) ; ménage local seul (`git branch -d`). Schéma `agent/{server}/RM{id}-titre` réservé à l'orchestration distribuée.

## Source des worktrees, emplacement des envs (RM3209)
Réglages d'INSTANCE, admin seul (`pm.config.local.yml`, jamais l'environnement). `git.worktree_source` : `central` (défaut) = `<ws>/repos/<repo>.git` ; `per_user` = `<dossier des dépôts>/<repo>` du dev (`PM_REPOS_DIR` de son `<core>/var/users/<user>/.env`, défaut `~/repos`). `git.envs_layout` : `project` (défaut) = `<ws>/envs/<env>` ; `user` = `<ws>/envs/<utilisateur>/<env>`. En `per_user` : `pm-branch-start --worktree` depuis SON dépôt (refus sinon) ; `pm-env-init` ne crée pas de dépôt partagé ; envs existants déplacés par `pm-env-relocate --plan`, jamais à la main. Seul résolveur : `pm_worktrees`.

## Plusieurs tickets dans une session
Risque vécu : commit d'un ticket sur la branche d'un autre. Avant chaque commit : `git branch --show-current` = ticket commité. Un worktree par ticket plutôt que des checkout successifs : `pm-branch-start <RMid> --worktree` crée `<repo>-<RMid>-s<seq>` et une branche discriminée par session `<RMid>-<slug>-m<PMid>-s<seq>` (`m<PMid>` = `PM_MACHINE_ID` du `.env`, `s<seq>` alloué une fois sous flock), enregistrés dans le registre de session `var/sessions/` (`pm-session-status show` les liste) ; deux sessions sur le même ticket ne se marchent pas dessus. Ménage : `pm-worktree remove <path>`. Forme courte `<RMid>-<slug>` = norme hors concurrence.
